# Plan

## How did you break the work into sessions?

We structured the development into six focused milestones, moving from core data foundations to business rules, search/bulk tooling, and finally analytics and front-end integration:

- **Session 1: Scaffolding, Authentication & Foundation** (Goals 1 & 2 baseline)
  - Initialized Node/Express backend and React/Vite client.
  - Defined PostgreSQL schema in Prisma (`User`, `Provider`, `Patient`, `Appointment`).
  - Implemented bcrypt password hashing, JWT authentication endpoints, and seed script with demo accounts.
- **Session 2: Appointment Availability & State Machine** (Goals 2 & 4)
  - Built single slot creation, unbooked slot editing, archiving, and restoring.
  - Implemented the full appointment status state machine (`AVAILABLE → REQUESTED → CONFIRMED → CHECKED_IN → COMPLETED`, `NO_SHOW`, `CANCELLED`).
  - Enforced post-check-in cancellation locks and no-show time constraints.
- **Session 3: Clinical Care Team & Visit Notes** (Goals 3 & 5)
  - Implemented `AppointmentSupport` for supporting providers on care teams.
  - Added visit notes API with author-only edit enforcement and care-team authoring rights.
  - Created provider combined schedule endpoint returning both primary and supporting appointments.
- **Session 4: Search, Filtering, Bulk Generation & Export** (Goals 6 & 7)
  - Implemented multi-parameter search, server-side sorting, and pagination for appointments.
  - Created recurring bulk availability generator with schedule conflict detection.
  - Implemented single-day CSV export adhering to RFC 4180.
- **Session 5: Audit Log, Unconfirmed Alerts & Analytics Dashboard** (Goals 8, 9, 10)
  - Built append-only `AppointmentHistory` timeline logging actor, timestamp, status changes, and reasons.
  - Implemented the 24-hour unconfirmed alert engine with the 1-hour reappearance rule for dismissed alerts.
  - Created clinic dashboard metrics and 8-week weekly no-show rate calculations.
- **Session 6: Polish, Full 10-Goal Audit, Verification & Documentation**
  - Conducted end-to-end audit, identified and resolved edge cases (reassignment endpoint, front-desk confirm permissions, SVG chart, interactive UI modals).
  - Built in-memory automated test suite verifying all 10 goals against live PostgreSQL.
  - Authored comprehensive architectural and operational documentation.

## What order did you build in, and why that order?

1. **Authentication & Roles first**: All downstream features depend strictly on knowing *who* is making the request (`FRONT_DESK` vs `PROVIDER`), and whether a provider owns the schedule. Establishing the JWT middleware and role checks first eliminated subsequent refactoring.
2. **Entity & Status Lifecycle second**: The core value proposition of a clinic scheduling system is the appointment state machine. Establishing how a slot transitions from `AVAILABLE` to `COMPLETED` created the backbone that care teams, notes, and alerts attach to.
3. **Care Team & Notes third**: With appointments functional, we layered on multi-provider care teams and clinical observations.
4. **Search, Bulk & Export fourth**: Search and bulk generation depend on having a populated schema with realistic appointments to test filtering and collision detection.
5. **Dashboard, Timeline & Alerts last**: These are aggregation and auditing features that consume the events generated by earlier goals. Building them last ensured we had real status transitions and notes to display.

## What did you cut when you ran short?

1. **External SMS/Email Notifications (Twilio / SendGrid)**: We considered sending real SMS reminders to patients. Because third-party API keys introduce external billing dependencies and webhook complexity for reviewers, we focused entirely on the internal front-desk alert drawer and operational UI.
2. **Patient Self-Service Booking Portal**: The scenario specifically highlighted a front-desk coordinator and provider workflow. We concentrated on the staff day-sheet and provider view rather than expanding scope into an external patient-facing portal.
3. **Interactive Drag-and-Drop Calendar**: While visually appealing, a full drag-and-drop calendar widget often obscures edge-case errors (like concurrent conflict errors or partial overlap warnings). We opted for a high-density, searchable table and dedicated modal inspection dialogs that make state transitions and conflict errors unambiguous.
